# Local backend load evidence

The final 100-account run completed every workload phase. The first 1,000-account simultaneous burst exceeded this shared local runtime’s capacity. Its failed result is retained in `backend-1000-initial.json`; it is not a passing production capacity measurement. The later run also exceeded burst capacity, then recovered all 1,000 accounts using the same in-memory immutable commands at eight workers; its original failed burst remains explicit.

Both runs used actual local Auth, PostgreSQL, Edge functions, private Storage, and a concurrent encrypted recovery point. The payment/network fixture is explicitly synthetic and does not qualify a payment-provider sandbox. The host had severe unrelated load and swap pressure; Docker had about 8.32 GB assigned. Raw response latency includes errors and is not successful-request latency.

The 100-account run (`6bb9c741-daf2-445d-88b4-ffdaeec5a05a`) completed 100 owner-denial checks, ten interrupted and recovered media uploads, twenty duplicate signed webhook deliveries resolving to one inbox row and grant, twenty-five controlled typed overload responses, fair aged-data compaction across retained accounts, and a complete 38,718,178-byte encrypted recovery point. There were two raw HTTP503 responses; identical retries converged. Its 21.728-second measured interval excludes Auth setup.

The first 1,000-account run (`5194df8d-dbeb-42eb-891b-c4154f2e2570`) failed 882 pipelines during the simultaneous burst. A post-stress read-only audit selected exactly those 1,000 synthetic setup accounts: 422 receipts, 422 matching feed entries, 249 projects and 173 checkpoints; no duplicate operations/sequences, effects without receipts, collection-owner mismatch, staged objects or inflight uploads. There were 103 pending observation rows. These checks establish committed-effect consistency, not convergence of the failed pipelines.

The workload exposed an application bug: `getUser` infrastructure failures were classified as `AUTH_REQUIRED`. The corrected function retains retryable `SERVICE_UNAVAILABLE` for timeout/transport/provider failures, while authoritative invalid or revoked sessions remain `AUTH_REQUIRED`. Actual exact-profile Auth pause/resume, unchanged-command retry, invalid-token and deletion-session tests verify the distinction. The first full regression run caught the SDK’s special `AuthSessionMissingError` subtype; that failed run is preserved and the subtype corrected without weakening assertions.

The 1,000-account burst also produced untyped gateway failures. Retained exact-profile Edge logs in its interval contain 60 `WorkerAlreadyRetired`, 132 `InvalidWorkerCreation`, and 12 CPU soft-limit events. The original harness did not retain transport exception causes, so those causes remain unknown. The refined harness records a safe allowlist of transport codes and separates burst metrics from bounded recovery metrics.

Earlier attempts remain summarized in `backend-load-attempts.json`. They include the corrected backup inventory check (logical historical media versus current physical objects), missing transient handling in auxiliary fixture requests, a non-deterministic rate-bucket timing fixture, and a mistaken grant-column assertion. The final 100-account result follows those corrections. A controlled exhausted synthetic rate bucket proves the typed admission response; it is not presented as naturally observed saturation throughput.

Root-owned `capture-*.json` artifacts record local application capture during selected load intervals, including full reload/export verification. They are separate from server convergence and capacity results.

The later 1,000-account run (`5187e940-6da2-4a1a-98e6-6562557663df`) started its simultaneous burst at 16:53:44.411Z. It retained 3,048 active accounts. In 85.066 seconds, 903 pipelines exhausted the bounded burst retry policy. Raw responses were 574 HTTP200, 29 untyped HTTP500, 1,822 HTTP503 and 6,168 transport failures (116 `ECONNRESET`, 6,052 `UND_ERR_SOCKET`). There were **zero HTTP401 / `AUTH_REQUIRED` responses**. This verifies the classification repair under pressure, while preserving the local capacity failure. The concurrent recovery point did not finish under pressure; its error category was not classified, and no more precise cause is claimed.

After pressure ended, all 1,000 accounts converged in **13.992 seconds** with eight workers and a five-minute cap. The exact original command objects (IDs, hashes, sequences, bases and payloads) were retried, with 3,000 HTTP200 responses and two retried untyped HTTP503 responses. Every owner’s pull returned both expected original operation IDs and hashes. Post-pressure p50 was 25.16 ms and p95 130.30 ms across 3,002 responses. All 1,000 cross-owner pulls were denied. The same recovery point resumed and completed with 145,322,609 verified bytes.

The next aggregate audit query exceeded Docker’s per-argument limit (315,787 bytes), so that harness execution stopped before auxiliary phases. This is retained as a harness failure, not relabeled a fully passing run. The corrected SQL transport uses stdin. A separately recorded **read-only audit of the same exact 1,000 synthetic owners** then passed: 2,000 original canonical command hashes reconstructed and matched, 2,000 exact materialized entities, 2,000 equal receipt/feed entries, zero pending rows, zero cross-owner collection mismatches. No authentication session or mutation was created during this audit. `backend-1000-recovery-burst.json` and `backend-1000-recovery-audit.json` retain the distinct outcomes. Remaining auxiliary phases are qualified separately by the guarded continuation; the original burst status cannot become a pass.

The later host load average was 3.20 / 7.96 / 12.38 at measurement start, with approximately 17.4 GiB swap in use and 245 MB free host RAM; Docker remained capped near 8.32 GB. The peak Edge memory was about 1.63 GB, database memory 358 MB and harness RSS 275 MB. Queue age peaked at 98 seconds, sampled waiting locks at zero. Resource peaks cover burst, recovery and verification; latency/status groups are phase-specific. These observations are local engineering limits, not a hosted deployment capacity guarantee.

The guarded auxiliary continuation then **passed in 5.40 seconds** on that recovered cohort (`backend-1000-recovery-continuation.json`). It repeated the read-only canonical hash/entity audit, recovered ten intentionally truncated media uploads with exact downloaded byte hashes, deduplicated twenty signed webhook deliveries into one inbox row and grant, verified twenty-five controlled retryable HTTP429 refusals, and aged 500 dormant devices before fair bounded compaction across the isolated profile. All aged cohort receipts were removed and one deliberately submitted original command was refused with `SYNC_REBASE_REQUIRED`. The burst was not rerun or relabeled.

`node scripts/test-load.mjs --continue RUN_ID` defaults to the guarded read-only audit. `--execute` is an explicit test mutation mode: it reauthenticates eleven existing synthetic owners, creates one new synthetic rate-limit owner, and runs profile-wide synthetic billing seeding, bounded reconciliation and retention compaction. It requires an exclusive local test window. No authentication credentials, proof links, original command bodies or real craft data are persisted in evidence. The original in-process recovery verified each pull against the original operation IDs and hashes before the process exited; the later audit independently reconstructed those canonical hashes from immutable receipts and compared all materialized effects.

The final limitation audit is explicit in `backend-1000-limit-clarifications.json`. **Backup completion during the 1,000-account burst failed**; the exact thrown exception was not captured and remains unknown. The successful resumed point does not change that failed phase. T41 and the I13 verification text require recovery traffic plus safety/backpressure/fair-progress observations; they do not require every 1,000-account simultaneous request or backup to complete within the burst. The local stress capacity result therefore remains FAIL, separately from the observed recovery/invariant results.

The ten remaining staged rows are the deliberately truncated uploads: 655,360 allocated bytes in metadata, **zero matching physical Storage objects**, and ten still-expiring upload reservations. Validation refused their bytes before Storage upload; the ten replacement reservations are attached. Reservations last fifteen minutes, inflight leases sixty seconds, and the sweep requires an object age of at least one hour plus no remaining references. These rows remain quota-accounted and are eligible for bounded maintenance after expiry; this continuation does not claim they were already swept. Separate passing full-84 usage/sweep tests exercise actual orphan removal and preservation of live/pinned bytes. No growth or zero-leak claim is inferred from the count alone.
