# Database and object recovery

Maker JSON exports and service recovery points solve different problems. The local operator driver creates an exported PostgreSQL repeatable-read snapshot, a custom-format database dump and an inventory of every verified immutable object in that snapshot. It pins the inventoried objects against ordinary garbage collection, copies bytes with concurrency two, validates every declared length/SHA-256 and reads back the persisted copies. A missing or corrupt copy leaves the point incomplete. Account deletion can override live-object pins; a racing backup can therefore fail safely.

The independent recovery directory is `.gstack/recovery/<profile>/<point UUID>`. Database, manifest and object copies use AES-256-GCM with random per-file nonces. The key is outside every historical point at `.gstack/recovery-keys/<profile>.key`; losing it makes recovery unavailable. These paths are private and ignored by Git. Plaintext status indexes contain only operational IDs, hashes, counts and dates. The local implementation uses separate files from primary Docker storage but shares the host and disk failure domain. It is **not evidence of physically independent disaster storage**. A hosted activation must qualify encrypted independent object/database storage and key custody with actual accounts.

A complete daily point expires seven days after capture. The scheduler makes one daily backup due after a successful run, giving seven daily points under normal operation. Explicit manual drills can create additional points; all retained bytes are separately metered. Expiration removes actual encrypted files and fsyncs the parent directory before marking the catalog expired or completing deletion receipts. The catalog tracks accounts with text-only craft data as well as media owners. A restore rebuilds this catalog from the current independent inventory, so an older primary database cannot forget later retained copies. Unfinished points remain incomplete and visible to retention accounting.

Each restore drill creates a uniquely named `lm_restore_<UUID>` database in the exact local PostgreSQL instance and a separate `.gstack/restores/<profile>/<UUID>` object directory. Every drill is registered before database creation and blocks deletion completion while its artifacts remain. Successful and failed drills drop the exact isolated database and remove/fsync object copies in `finally`; only redacted evidence remains in `.gstack/restore-evidence`. A bounded expiry worker reclaims registered orphan artifacts after a process interruption. No Auth, REST, Storage or public gateway endpoint routes to that database. The gate starts false. The runner verifies database/manifest/object hashes, fetches the **current** independently stored erasure ledger, verifies its hash-chain watermark and bounded page chain, and applies every authorized deletion before readiness. An unavailable, stale, changing or malformed ledger leaves the gate false. It never trusts an erasure ledger copied into a historical point.

Ledger replay reconstructs the original narrow deletion receipt hash if the primary commit was lost after append. Deleted owners' restored craft/Auth/live-object records are removed, their media are excluded from restored copies, and minimal purchase linkage follows the detached-principal policy. All restored refresh sessions are discarded; surviving accounts sign in again. The ready marker records only this completed drill at a point in time. It does not promote traffic. Actual activation must repeat the current ledger handshake and install ongoing deletion reconciliation before routing any request; a later deletion can change the watermark after a drill. The original maker receipt capability continues to address the reconstructed hash; it is never printed or stored raw.

The local driver bounds a dump at 256 MiB compressed metadata, object size at 8 MiB, inventory at 100,000 records, copy concurrency at two, and a backup at four minutes. Before copying it reserves space estimates while leaving at least 2 GiB free. Those are local qualification limits, not product capacity promises. Restore drills report actual snapshot age (RPO) and elapsed time (RTO) against provisional 24-hour/four-hour targets; an unmet target stays unmet. Production traffic promotion, independent-host failure testing, managed Supabase upgrade qualification and monthly scheduling remain explicit release gates.

Run `npm run test:server -- --suite recovery` only on the isolated synthetic profile. The tests create real Auth/data/media, take snapshots, append a later authorized deletion before the primary barrier, restore into isolated databases, inspect erased records, recover unchanged media hashes, deny missing/current-ledger failures and corruption, and exercise worker fencing. They never drop the live primary database. Cleanup of an isolated drill uses only the exact generated database ID and its matching private directory.
