# Loopmark expansion: cloud, purchases and native apps

Planning input, 18 October 2026. This supersedes the earlier decision to exclude cloud sync, checkout and iOS/Android packages. The user explicitly selected all three additions and requested deep brainstorming and gstack planning. This document is not a claim that those additions are implemented or live.

## Intent and non-negotiable outcomes

A maker can capture a restart note quickly without a connection, find it on their other signed-in devices after synchronization, and recover their data independently of either a purchase or a provider. The existing next-step-first experience remains the product's center. Account setup, payment and synchronization never sit in the critical path of saving the first three active projects.

Deliver web plus iOS and Android application packages, optional account-backed synchronization, a real one-time upgrade, restore-purchase behavior, export/restore, account deletion, operable production configuration and independently verified failure recovery. A native folder or mocked checkout alone is not completion. Sandbox evidence, local builds, signed binaries, physical-device tests and live publication must be reported separately.

Preserve every accepted local requirement R1–R9 and all repaired data/draft/offline behavior. The local foundation passed 209 browser journeys, 33 data tests and four isolated scale checks on worker cache `loopmark-ad60daeda70e`; freeze its verified commit before integration. Do not rewrite or delete the existing browser database. Existing unrestricted research users keep access to their existing collection; migration may not lock them out of their notes, history or exports.

## Proposed product and commercial rules

1. Guest mode works offline. New release users may keep three active projects free; finished projects do not consume an active slot. Finishing, deleting, viewing, exporting and restoring data are always available. A free import above the cap remains readable/exportable; it cannot silently discard records. A new fourth active project or reopening beyond three offers upgrade or return. Existing research collections receive an explicit migration entitlement rather than retroactive loss of access.
2. The one-time upgrade unlocks additional active projects within technical capacity limits. All saved checkpoints remain viewable in free, upgraded, imported, legacy and revoked states; history access is never a paid unlock. The UI distinguishes a commercial limit from a technical capacity limit.
3. The initial hypotheses remain India ₹299–₹599 and international US$4.99–US$7.99. Prices, taxes, store tiers and provider availability are configured per market; the client displays the provider's actual localized price. The plan does not authorize charging people or claim these hypotheses support recurring cloud costs.
4. Cloud storage has an explicit byte quota and a usage display. The initial collection remains within the current complete-backup envelope: 200 projects, 1,000 checkpoints and 48 MiB of serialized v1 library data, including base64 media expansion. Server admission checks that envelope as well as actual object bytes. Increasing cloud storage above it requires a separately implemented and roundtrip-tested binary/streaming backup format first. A full cloud quota stops additional uploads, retains local saves, explains which items are pending and offers export/cleanup. Do not promise unlimited lifetime cloud storage from a one-time payment. Whether a recurring cloud tier is commercially needed is a separate evidence-driven decision; it must not be silently bundled into this one-time offer.
5. Native purchases use the store-supported one-time digital product and restore flow. Web checkout uses an approved merchant provider. A shared server entitlement ledger reconciles verified purchases; a return URL or client boolean cannot grant access. A purchase never changes project ownership.
6. Account login is optional for local use but required before purchasing a cross-platform entitlement or connecting cloud. Show this requirement before opening checkout. A purchase on one platform maps to one account; account transfer/recovery requires a documented support path and cannot be performed by changing a client ID.

## Account and privacy contract

Use managed authentication with email sign-in and recovery. Prefer a code/magic-link flow only after native deep-link and delivery feasibility is established; provide explicit expiry/retry feedback. OAuth is not necessary for release and must not create an unplanned Sign in with Apple dependency. Production email delivery, redirect allowlists and abuse controls are required configuration, not assumed installed features.

On first connection, show local and cloud project counts and the destination account. Require an explicit action to add the local collection to that account. No automatic upload on merely entering an email address. Existing IDs are retained when the account has no conflicting lineage; conflicting imports become separately identified copies with source IDs recorded. Never use last-write-wins to silently erase metadata edits or overwrite a complete collection.

Each local collection is namespaced by guest or stable account ID. Sign-out stops synchronization and subscription listeners, aborts in-flight account-scoped work, clears session credentials and asks whether to retain a device copy or remove it. A retained copy is clearly marked local and cannot upload into a different account without a fresh migration preview. Account B cannot read account A through cached queries, drafts, files, signed URLs or notification events.

Account deletion requires recent authentication and explicit confirmation. Explain cloud deletion, local-copy behavior and purchase-retention exceptions before action. Immediately disable account access in database policies and server commands; merely deleting an auth user is insufficient while an issued JWT remains valid. Delete owned records and media through an idempotent job with a visible pending/completed status, removing owned Storage objects before deleting the auth user. Revoke sessions and stop sync immediately. Preserve only legally/operationally required payment records with a documented retention purpose. Do not claim deletion of provider backups sooner than the verified provider policy permits. Supply a public deletion request route for store requirements and a privacy/support page before distribution.

Keep local commit independent of network success. The local record and its outbound operation must commit atomically. Use IndexedDB on web; select a maintained native transactional database/file bridge after a focused compatibility test, not a key-value preference store for large photos/audio. Reuse typed domain invariants, backup validators and receipt semantics across implementations. Platform interfaces cover secure session storage, media capture, files/share, deep links, connectivity and purchase UI; avoid platform checks scattered through components.

Proposed backend: Supabase Postgres/Auth/private Storage with migrations and server functions in the repository. This is a recommendation, not a created cloud project. Every user-owned row has an immutable owner derived from the authenticated server context. Row-level security and private object policies enforce ownership even if a client bypasses the UI. Service credentials stay in server secret configuration and never enter Vite bundles, native resources, logs, exports or browser storage.

## Synchronization protocol

Entities: accounts/profiles, projects, immutable checkpoints, media objects, mutations, change cursor, deletion tombstones, account devices and entitlement records. Projects use a server revision integer, not device wall time, for concurrency. Checkpoints keep user-facing capture time plus server acceptance ordering, allowing clock skew without using that timestamp as authority.

An operation has `{operationId, accountId, deviceId, entityId, kind, baseRevision, payloadVersion, payloadHash, payload}`. The server derives account identity from auth, validates ownership and limits, and processes the operation and receipt in one database transaction. Repeating the same ID/hash returns the previous result; reuse with different content is rejected. Client-generated IDs support offline creation. Retries use capped exponential backoff with jitter and manual retry; validation, conflict and authorization errors are not endlessly retried.

Checkpoints from multiple devices append without loss. Concurrent project metadata edits return a conflict with both versions; the user chooses the complete current or incoming values, or saves an explicit merged revision. Finish/reopen uses the same revision rule. Deletion wins against stale edits through a tombstone; a user can deliberately recover a copy with a new ID. Tombstone pruning must not resurrect devices that have been offline for months: require a full rebase from a retained cursor boundary before accepting their old operations.

Pull changes by an opaque monotonically increasing server cursor, ordered deterministically and paginated. Apply a batch and advance the cursor in the same local transaction. Realtime events are only a wake-up hint. Reconnect, foreground and explicit sync always reconcile the durable feed, so a missed event cannot lose data. Serialize sync ownership per account/device and coordinate multiple browser tabs. Refreshing an expired session must not duplicate writes or send the prior account's queued records under a new account.

Media uploads use private owner-scoped paths and content hashes. Validate byte size, supported content and declared quota server-side; client checks are user feedback, not the security boundary. Upload to a staged object, verify it, then attach it through a committed operation. Checkpoint text may sync with an explicit pending-attachment state; the UI must not report a complete synced checkpoint before its required media is available. Failed uploads remain retryable locally. Orphan cleanup is bounded and never deletes an object referenced by a committed checkpoint. Downloads use short-lived authorized URLs; exports embed bytes and never leak URLs/tokens.

Restore remains an explicit destructive operation within its chosen local collection. For a connected collection, preview the cloud effect and require recent revision review. Implement restore as an idempotent server collection-replacement command with an epoch change, then rebase devices. Do not translate an old full backup into hundreds of uncoordinated ordinary edits that can interleave with another device. Require a current export or explicit acknowledgement before replacement. Offline restore creates a separate local recovered collection until the user chooses a cloud destination.

## Billing and entitlement contract

The server creates orders with a stable purchase-attempt ID and server-chosen product/currency/amount. It stores the account binding before redirecting to the provider. The client sees cancelled, pending, verifying, paid and failed states. The webhook verifies the raw request signature and event identity, durably stores the authenticated event before acknowledging it, fetches authoritative provider state when needed and records one entitlement transition transactionally. Duplicate/out-of-order events, refunds, revocation and restoration must converge. A scheduled reconciliation job recovers events after the provider's finite retry window; provider retry delivery alone is not durable entitlement recovery. Do not trust a payment-complete browser callback.

For native IAP, compare a maintained cross-platform purchase service with direct StoreKit/Play server verification. Select only after checking actual Capacitor support, one-time product support, fees, account mapping and refund/restore semantics. Production keys and store product identifiers are configuration requirements. Sandbox purchases may be tested without claiming real revenue.

Previously verified one-time entitlements are cached for offline access. A temporary network/provider outage must not remove paid local features. Revocation is applied after authoritative reconciliation, preserves all existing data and export, and blocks only new over-cap actions. Client clocks cannot extend subscription-like periods because the proposed product is non-consumable. Tamper resistance is server-enforced for cloud capacity; perfectly enforcing a wholly offline local limit is not a security promise.
