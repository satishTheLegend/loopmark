### Eleven review lenses

1. **Architecture:** Keep draft storage separate from immutable saved checkpoints and treat drafts as tentative data. Worker readiness belongs in a small platform module, while application status renders it; no remote dependency is introduced. The browser profile remains the single point of loss, mitigated by full backup rather than false durability claims.
2. **Errors:** Registration rejection and install failure must be visible and retryable. Draft-write failure must never claim recovery success or close over user text. Storage, media and conflict errors remain associated with the attempted action; the registry below defines observable rescue behavior.
3. **Security:** New persisted drafts contain the same private notes/media as saved records and need bounded validation and no remote transfer. Restore is destructive only after explicit confirmation; external media and executable content stay rejected. No credentials, endpoint or tenant boundary is added, so authentication infrastructure would not improve this release's threat model.
4. **Data/interaction edges:** Close, Escape, reload, browser Back, repeated Save, deleted projects, restore and another tab's edits must not silently corrupt or revive work. A save must consume the intended snapshot only after repository commit; draft cleanup must not erase a newer tab's tentative input. The data and root test owners must prove these schedules, not assume event ordering.
5. **Code quality:** Keep platform state and draft persistence in focused modules, reuse field validation and preserve the original domain model. Do not add a new state framework or generalized repository abstraction. Duplicate UI state checks are acceptable only when they enforce a distinct boundary; final code review checks for contradictory save/cleanup ownership.
6. **Tests:** Existing happy paths are valuable but do not prove enlarged text, real worker failure/update state or interrupted drafts. Add tests at the actual UI/storage/worker boundaries, including loss-prevention negative paths and rollback. Use isolated contexts and deterministic fixtures; synthetic microphone/device evidence must retain that label.
7. **Performance:** Full-library reads and JSON/media cloning are the largest bounded costs. Measure actual 20/200 saves, 50/500 search/reload and 10/100 media restore before optimizing; report bytes and the test machine. A 48 MiB library cap bounds storage, but does not guarantee acceptable memory on every device.
8. **Observability:** Local user-visible errors and reproducible diagnostics serve this serverless utility. Remote logs, dashboards and analytics would send private information and are outside scope. Worker status, draft recovery state and error messages must identify whether the next action is retry, reopen, export or restore.
9. **Deployment:** Keep service-worker updates waiting until safe closure/reopen and retain earlier hashed assets on deployment. Backward compatibility of saved records is more important than immediate worker activation. A local build can verify lifecycle mechanics; hosted headers, origin stability and real installation require a deployed-origin check.
10. **Future:** These changes are reversible application code and preserve contract v1; a later cloud feature still needs its own sync/auth conflict design. Drafts must not become a second unsynchronized source of truth for saved checkpoints. Keep private notebook indexing protections and concise subject-specific docs so future work starts from actual evidence.
11. **Design:** The next step remains the dominant project content; offline/draft status must support, not overwhelm, capture. Use the existing warm palette, semantic labels and native controls. Every new status needs loading, success, error and recovery copy; final desktop/mobile rendering and keyboard checks remain mandatory.

## Engineering plan review

Target: CP2–5 implementation and tests, checked against the working source, not only the proposed text. Scope accepted as-is under the user's delegated corrective decisions. The existing arrangement changes roughly a dozen production modules/scripts and adds focused draft, offline and media-validation modules. Inlining these into App/data would reduce filenames while coupling unrelated lifecycle responsibilities; it would not reduce the approved behavior. Keep the separated modules and existing v1 domain model. No new infrastructure, framework or production package is justified.

The new patterns use built-in browser facilities [Layer 1]. IndexedDB transactions provide atomic rollback within one database; completion does not establish immunity to device or profile loss. Draft cleanup is in another database and therefore needs retry-safe saved-record receipts. Waiting service workers avoid replacing the code underneath open work. These choices match the [MDN transaction model](https://developer.mozilla.org/en-US/docs/Web/API/IDBTransaction) and [web.dev lifecycle guidance](https://web.dev/articles/service-worker-lifecycle). This research was a read-only official-source check, not an outside-model review.

### Architecture

Saved records remain authoritative in `data.ts`; drafts are tentative input in `drafts.ts`, keyed by new/edit/checkpoint context. Draft compare-and-swap prevents silently replacing another tab's draft. Domain save receipts bind a stable operation token to its input and result in the same transaction, preventing a successful save from being duplicated when draft cleanup fails. Restore validates the file/media before opening its atomic replacement transaction, checks the collection revision shown in confirmation, and invalidates old receipts on replacement. Worker state is exposed by `offline.ts`, with generated cache checks rather than `navigator.onLine` as evidence of readiness.

```text
FORM / DRAFT                                      SAVED LIBRARY
open -> read draft -> empty/recovered/error        create/checkpoint -> validate + fingerprint
change -> serial CAS write -> kept/conflict/error    -> receipt already exists?
save -> flush -> stable token -------------------->   yes: same input/result -> return prior result
                                                      no: record + receipt -> transaction complete
     <- committed result ------------------------  abort: preserve prior library + report failure
clear matching draft -> close + saved notice
     \-> cleanup failure -> warning; retry token returns the existing saved result

BACKUP
file -> size/schema/container/decode -> preview(collection revision)
confirm -> compare revision inside replacement transaction
  changed -> retain current library + incoming preview -> review latest -> confirm again
  same -> clear/add/metadata/receipts -> complete; abort rolls all changes back

OFFLINE
register -> installing -> active -> CHECK_OFFLINE_READY -> all cache assets present?
failure -> visible retry      |                              yes: ready / no: repair
new version -> waiting ------+-> old windows close -> activate -> new readiness check
```

The single browser profile remains the durability boundary. Downloaded backups and explicit limitations are appropriate; claims of cloud recovery are not. Release distribution remains the existing generated static app plus worker and manifest. Stable-origin HTTPS deployment, physical installation and remote CI are deferred external execution, not missing local code.

### Performance

The repository reads/clones full project objects, and media lives in JSON data URLs; these are bounded but can consume substantial transient memory. Restore performs schema/container checks and photo decode before transaction, then revalidates at the repository boundary. That duplicate validation is deliberate protection against callers bypassing the file picker. No N+1 network path exists. Photo decode has a timeout, draft open has a timeout, and worker verification has a timeout. Every draft change currently writes a full current snapshot; do not infer media-heavy typing performance from text-save timing.

Measured targets and exact fixture bytes are recorded in `performance-review.md`. The measured integrated build passes the declared lab budgets, so virtualization, a new cache, blob migration or speculative memoization is not warranted. Final save-path changes require the short scale suite to run again. Maximum-capacity memory, physical low-end devices, long sessions and field INP remain unmeasured and explicitly outside the lab claim.
